# EzyFox Library: Bean, Binding, and discovery

Sources: [Overview](https://youngmonkeys.org/projects/ezyfox-library?lang=vi), [Bean](https://youngmonkeys.org/ezyfox-library/guides/introduce-ezyfox-bean?lang=vi), [bean creation order](https://youngmonkeys.org/ezyfox-library/guides/ezyfox-bean-bean-creation?lang=vi), [annotations](https://youngmonkeys.org/ezyfox-library/guides/ezyfox-annotations?lang=vi), and [Reflections](https://youngmonkeys.org/ezyfox-library/guides/how-reflections-scans-classes?lang=vi).

## Module boundaries and lifecycle

- `EzyBeanContext` manages properties, singletons, and prototypes. The guide favors constructor injection. Use `@EzySingleton` for services without request state and `@EzyPrototype` when you need a separate instance, not to work around wiring errors. In a plugin, keep the controller → service → repository flow and let the existing container create beans. Do not use `new` for services managed by the runtime or start a separate context.
- The documented order is `@EzyConfigurationBefore` → `@EzyConfiguration` → singleton, prototype, and properties beans → `@EzyConfigurationAfter`. Register factories in the appropriate phase and use only beans already created in the later phase. Some configurations only log a warning when a dependency is missing. Check startup tests for the required beans and routes, not just the exit code. Break dependency cycles by extracting a policy or helper or reversing a dependency through an interface, not through a global lookup.
- Reflections reads class metadata from packages, URLs, or VFS, filters the input, and indexes annotations and inheritance. It does not instantiate beans. A missing scan package, a missing SDK class in the artifact, an annotation for the wrong runtime, and an inactive dependency are different problems. Compare `module.properties`, the real classpath, the sample's `@ComponentsScan`, and ZIP contents rather than expanding the scan to the entire core.
- [Binding](https://youngmonkeys.org/ezyfox-library/guides/introduce-ezyfox-binding?lang=vi) and [marshalling and unmarshalling](https://youngmonkeys.org/ezyfox-library/guides/ezyfox-binding-marshal-unmarshal?lang=vi) describe mappings for DTOs, collections, and maps. Treat Socket and HTTP input as untrusted: keep the field set small, validate sizes and types, and avoid serializing domain entities or complete membership data. The bean context, serialization, and authorization are separate concerns.

**Useful tests:** Start Admin and Web separately with real constructor wiring, and make smoke tests fail if a dependency is missing. Run two sessions at once to verify that singleton fields do not retain the actor. See [EzyHTTP](ezyhttp.md) for passing caller identity to the service and [EzyData](ezydata.md) for scoping queries.
