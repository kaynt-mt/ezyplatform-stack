# EzyFox Server: real-time research, not an MVP dependency

Sources: [Overview and Samples](https://youngmonkeys.org/projects/ezyfox-server?tab=samples&lang=vi), [architecture](https://youngmonkeys.org/ezyfox-server/guides/ezyfox-server-architecture?lang=vi), [socket events](https://youngmonkeys.org/ezyfox-server/guides/handle-socket-events?lang=vi), [client requests](https://youngmonkeys.org/ezyfox-server/guides/handle-client-requests?lang=vi), and the [ES6 SDK](https://youngmonkeys.org/ezyfox-server/guides/ezyfox-es6-client-sdk?lang=vi).

## Layers and protocol

- The server manages sessions, events, and zones. Each zone separates plugins from apps. Plugins usually handle zone-level events such as login; apps use command handlers for business logic. The examples show controllers and singleton or prototype handlers and distinguish the `EzySession` connection from the authenticated `EzyUser`. None of those layers grants access to business resources by itself.
- The SDK describes connection → handshake → login → app access, plus ping/pong and disconnection. Application messages use named commands. An open WebSocket or successful handshake is not yet a valid application session. The [login guide](https://youngmonkeys.org/ezyfox-server/guides/ezyfox-server-login?lang=vi) shows credentials and access tokens for a standalone server. When integrating with the core, use [EzyPlatform Socket](https://youngmonkeys.org/ezyplatform/guides/overview-of-ezyplatform-socket?lang=vi) rather than bringing the sample login flow or Admin tokens into the Web client.
- [Reconnection](https://youngmonkeys.org/ezyfox-server/guides/ezyfox-server-handle-reconnection?lang=vi) explains how clients reconnect but does not promise replay of missed application events. [Scale up](https://youngmonkeys.org/ezyfox-server/guides/ezyfox-server-scale-up?lang=vi) compares splitting servers with separating services. Local sessions and delivery across multiple nodes do not synchronize automatically. The [stress test](https://youngmonkeys.org/ezyfox-server/guides/ezyfox-server-stress-test?lang=vi) is a benchmarking example, not a load guarantee.
- TLS sockets and WebSocket TLS in the [WSS guide](https://youngmonkeys.org/ezyfox-server/guides/ezyfox-server-config-websocket-ssl?lang=vi) require separate infrastructure setup. Use WSS in deployed environments and check proxy connectivity and timeouts. Do not reuse sample keys or endpoints. Compose starts only Admin and Web automatically. The [sandbox report](../../plugins/test-report.md) confirms Socket binding and module registration, **not** the client protocol or end-to-end push delivery.

## Suggested investigation after the MVP

1. Keep HTTP and the database as the source of truth. Publish events only after commit. Include the event ID, resource ID, and minimum version in the payload. Refetch the record with authorization rather than sending the whole record.
2. Resolve the actor from a trusted Socket session. Check membership on subscribe, reconnect, and before fan-out, or enforce a reliable subscription revocation policy. Do not trust a client-supplied actor or role or use app names as ACLs.
3. Test anonymous access, cross-scope access, revocation during an open connection, disconnection and resumption, duplicate or reordered messages, and multiple nodes if deployed. Keep HTTP polling unless you can show fan-out preserves ACLs and reconnects work.
